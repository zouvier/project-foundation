# v0.1.3

This patch prepares foundation version `0.1.3` on top of `4cc81c280cdb5886f8bfb144d60e39dfd4d96005`. The existing public `v0.1.2` tag remains the upgrade baseline. Publication requires independent review of the frozen candidate and successful CI on the final commit; local validation alone does not publish a release.

The generated reviewer role now requires review of identified diff and untracked bytes, separates observed checks from builder reports, returns missing or failed checks to the builder, and leaves attributed task-record writes to an authorized coordinator or builder. Read-only reviewers cannot edit, install, fix findings or run mutating checks. A recommendation is distinct from acceptance. Reporting errors remain blocked delivery; only a permitted fallback may preserve attributed findings, and broader retries require fresh explicit approval.

The preserved custom orchestration prototype remains closed, source-only and excluded from generated projects; Orca is the chosen runtime. Its offline checks establish no production-worker behavior. Source documentation describes bounded Orca builder/reviewer work, artifact identity, reporting fallback and uncertain turn starts. The improvement plan defines finite tasks and decision gates. The source-only proposal ledger contains one entry, **P2-001: PROPOSED and unapplied**; it does not authorize its own implementation. P3, schemas, runtime and dashboard work remain outside this patch. No continuous overseer service, verified Daybreak behavior, production containment or productivity improvement is established.

Root package metadata and both generated foundation-version fields advance together. Application seeds remain `0.1.0`; dependency and runtime pins, contract and receipt schema versions remain unchanged. Generated projects stay independent, and existing consumer pins are untouched.

The reviewer role is Copier-managed. Projects adopting this version must use a separately approved pinned update on a clean branch, review the generated diff, resolve conflicts and run their acceptance commands. A locally edited `.project/roles/reviewer.md` may conflict with the corrected upstream role. The real-release fixtures cover ordinary `v0.1.2` adoption with preserved application edits; the synthetic upgrade matrix covers edits, deletions and managed-file conflicts, rather than every possible local reviewer-role edit. Never hand-edit Copier lineage or move the old tag.
