## First milestone: make the generated reviewer role safe for read-only review

**One gap, one behavior change:** replace the unconditional write/rerun instructions in `template/.project/roles/reviewer.md` with a bounded review handoff compatible with the existing source workflow.

- **Owner/scope:** one Codex builder edits only that role; the maintainer records checks in `docs/verification.md`. No other role, schema, task seed, preflight, runtime or existing workflow document changes. A separate fresh Codex reviewer reads the frozen artifact; the human accepts it. Role text remains provider neutral so generated projects retain independence; Codex-only selection belongs to the Orca dispatch, not a new adapter.
- **Required content:** inspect the task, exact diff/untracked bytes and artifact identity; report file-backed findings, limitations, actual versus builder-reported checks, and recommendation to the coordinator. Under read-only policy do not edit task records, install, fix findings or rerun mutating checks. The authorized coordinator/builder records attributed review evidence in the existing task format without turning a recommendation into acceptance. Request missing checks from the builder; revised bytes require new identity and review. Role names confer no permissions.
- **Reporting failure:** return findings through the permitted channel; report EPERM as a delivery blocker and let the coordinator preserve/capture the review against its artifact. Never silently broaden policy, retry unsandboxed, or infer success from turn readiness. Any broader retry requires fresh explicit approval. Do not attempt to fix Orca from the scaffold.
- **Dependencies:** freeze/identify the existing three-file artifact first; inspect effective Codex reviewer policy and installed Orca command support. A prepared foundation `.venv` with pinned dependencies is needed for checks; if absent, stop and report setup as unrun rather than installing implicitly. Full fixture acceptance requires the explicit install/network authorization described in README.
- **Acceptance commands (future implementation, foundation root):** `git diff --check`; `.venv/bin/python -B -m pytest tests/test_contract_schema.py -q`; then the README integration command: `FOUNDATION_INTEGRATION=1 .venv/bin/python -B -m pytest tests -q --basetemp=.artifacts/pytest`. Retain command, absolute cwd, environment, exit and log paths. The fixture suite must generate independent repositories for both profiles, exercise canonical commands and upgrades with edits/deletions/conflicts; skipped integration is incomplete acceptance. Inspect each generated `.project/roles/reviewer.md` against the source and verify no old unconditional edit/rerun instruction survives. Review a sample handoff with a failed check and reporting blocker; ensure it preserves both as unverified/blocked rather than claiming success. No model call is required for these maintenance checks.
- **Compatibility/release:** no JSON contract/version change. The role is Copier-managed, so adoption can conflict with local role edits; review that diff through a new immutable foundation release and each project's separately approved pinned update. Do not retag `v0.1.2`, edit answers/pins, release or adopt during this milestone.
- **Stop:** one role patch plus recorded evidence, independently reviewed exact artifact and human accept/reject decision. If checks, reporting or approval block completion, preserve the artifact and report the blocker; do not expand scope. This planning task stops before implementation.
